What does not change

  • No breaking changes. Every existing endpoint keeps its path, request and response. New data is added as new fields, new optional query parameters or new endpoints. The current 111 tests must keep passing unmodified.
  • Business rules stay where they are. The three delivery limits, ledger replay, PO invariants and rate snapshot are not duplicated. New read endpoints call the same service functions the write paths use.
  • Stored data is unchanged. No existing collection gets a new required field. Migration 002 only adds indexes and one new collection.

2 · Rules

Rules every addition must follow

These are the conventions the existing backend already uses. New code that breaks one of them is a bug, even if its own tests pass.

1 · Layering

Route → validate(schema) → controller → service → repository. Controllers stay thin and only call ok()/created() from utils/apiResponse.js. Business decisions live in services. Queries live in repositories.

2 · Response envelope

Success: { success: true, data, meta? }. Error: { success: false, error: { code, message, details?, requestId } } through AppError. List meta always comes from pageMeta(); new list extras go inside meta (for example meta.summary).

3 · Exact decimals

Quantities (3 dp), rates (2 dp) and money (2 dp) are Decimal128 in MongoDB, Decimal.js in code and strings in JSON, using QTY_SCALE, RATE_SCALE and MONEY_SCALE. Never Number() a quantity. Weighted averages are value ÷ quantity, as in avgRate().

4 · ObjectIds in aggregations

Mongoose casts ids in find() but not in aggregate(). Every $match built from query input must use toObjectId(). This was a known bug in the guide's reference code; B2, B6, B9 and B10 all hit it.

5 · Activity vs position

Activity (bought, sold, values, averages) uses the period [from, to] on business dates. Position (stock, PO remaining, supplier pools, buy needed) is the balance as of to. Never mix the two in one number. Default to is businessToday(BUSINESS_TIMEZONE), not UTC.

6 · Business dates

Dates are YYYY-MM-DD strings validated by businessDate and stored at UTC midnight. "As of a day" includes that whole day (endOfDayUTC). Technical time (createdAt) is only for ordering activity, never for accounting.

7 · Roles

All GET routes are open to OWNER and VIEWER. Every write (POST/PATCH) uses authorize(ROLES.OWNER). Read-only helper endpoints (capacity, last rate) are GET and open to both roles.

8 · Route order

Fixed sub-paths (/capacity, /summary, /last-rate, /export.csv) must be registered before /:id. Otherwise idParams rejects them with 422 VALIDATION_ERROR.

9 · Writes

Any write that affects stock runs in withTransaction, locks POs/materials through LockableRepository.lock() in sorted order, and replays the affected ledgers. None of the items here adds a new stock write; B17 wraps existing writes without changing them.

10 · Validation

Every query parameter is declared in Zod, with unknown keys rejected as today. Booleans use queryBoolean, never z.coerce.boolean (it turns "false" into true). Enumerations use z.enum. Lists (comma-separated) are parsed and each value validated.

Definition of done for every B-item

  • Zod schema, route, controller, service and repository code in the existing files named in the spec card.
  • Integration tests in tests/integration/ using the real replica set (mongodb-memory-server): happy path, validation, VIEWER access, and one edge case per rule.
  • README API table and "deviations" section updated; npm run check green.

B1Delivery capacity endpointP0BE
GET/api/v1/sales/capacity?poId&sourceCompanyId&saleDate&excludeSaleId

Why. The delivery form must show the same limits the server enforces, before the user presses Save (UI doc P0-1, pages 3 and 12–13). Today the numbers only arrive inside a 409 error after a failed save.

Query

ParamRuleMeaning
poIdrequired, objectIdThe sales order being delivered.
sourceCompanyIdoptional, objectIdChosen "Stock from" supplier. Without it the supplier limit is omitted and only the sources list is returned.
saleDateoptional, businessDateDefaults to businessToday(BUSINESS_TIMEZONE).
excludeSaleIdoptional, objectIdWhen editing a delivery, that delivery is not counted against its own limits (same rule as assertCapacity).

The key rule: use the ledger floor, not only the balance on the day

A save is accepted only if (1) quantity ≤ PO remaining, ≤ yard stock as of the sale date, ≤ supplier stock as of the sale date, and (2) the ledger replay after the save never goes negative on any later day (assertMaterialLedgerNonNegative / assertSourceLedgerNonNegative). For a backdated delivery, (2) can be stricter than (1). So the endpoint returns the floor: the lowest balance on any day from saleDate onwards. The floor is never higher than the balance on the day, so maxAllowedTons = min(PO remaining, yard floor, supplier floor), floored at zero. That is exactly the largest quantity the server will accept.

Blockers (returned, not thrown)

CodeWhen
PO_NOT_AVAILABLEPO lifecycle is CANCELLED (unless editing a sale already on this PO without raising quantity; the form handles that).
PO_COMPLETED new, read-onlyPO remaining is 0.

Blockers are returned in the 200 body so the panel can explain them without an error state. Only a missing PO (404 PO_NOT_FOUND) and bad input (422) are thrown.

Implementation

  • stock.service.js: add ledgerFloor(openingBalance, inflowDays, outflowDays, fromDate) next to findFirstNegativeDay. It replays the same day map and returns the minimum balance over all days ≥ fromDate, starting with the balance at end of fromDate. Add getMaterialFloor(materialId, fromDate, {excludeSaleId}) and getSourceFloors(materialId, fromDate, {excludeSaleId, sourceCompanyId?}). The second uses two aggregations grouped by (company, day) for purchases and (sourceCompanyId, day) for sales of that material, then replays each supplier in memory. That is one round trip for every supplier.
  • sale.service.js: extract the body of assertCapacity into computeCapacity({ po, sourceCompanyId, saleDate, excludeSaleId, session }), returning the limits above. assertCapacity calls it and throws exactly the same three codes as today. The 409 details gain yardFloorTons/sourceFloorTons, and maxAllowedTons becomes floor-based. That is additive and more accurate. Add saleService.capacity(query): load the PO with salesPORepository.findWithPosition, collect blockers, call computeCapacity without a session (read-only), attach sources.
  • sale.validation.js: saleCapacitySchema. sale.controller.js: saleCapacity. sale.routes.js: router.get('/capacity', validate(saleCapacitySchema), asyncHandler(saleCapacity)) placed above '/:id'.

Race with other users

Capacity is a read. Another save can land between the read and the user's Save. The server still enforces every limit inside the transaction, so this cannot corrupt data. The frontend refetches capacity on any 409 and after a successful save (F1).

Tests (tests/integration/sales-capacity.test.js)

  • Parity: create a sale at exactly maxAllowedTons → 201; at maxAllowedTons + 0.001 → 409. Run it three times, once for each binding limit.
  • Backdated case: a later delivery exists, so yardFloorTons < yardStockTons. Saving above the floor returns NEGATIVE_STOCK_HISTORY; saving at the floor succeeds.
  • excludeSaleId: editing a 5 t sale on a PO with 0 t left reports 5 t available.
  • Blockers: cancelled PO, completed PO, date before PO, inactive supplier. Each gives 200, a non-empty blockers list and "0.000".
  • /sales/capacity is not swallowed by /:id. VIEWER gets 200. Unknown query key → 422.

Implementation

Scale note: contains-regex scans are fine at yard scale (tens of thousands of rows). If lists grow past ~200k rows, add a MongoDB text index; the API contract does not change. Tests: one per new field; "GJ 03 AX" matches GJ03AX4521; regex characters in input are escaped; search combines with the other filters (AND).

Declare every index in the schema, not only in the migration

Migration 001 uses syncIndexes(), which drops any index not declared in the Mongoose schema. So schema.index({ createdAt: -1, _id: -1 }) is added to Purchase, SalesPO and Sale, and 002 syncs them. An index created only inside the migration would be silently removed by the next sync.

Why. A refresh token in JSON has to be stored by page scripts, so any XSS can steal a 30-day session. An httpOnly cookie is never readable by JavaScript (UI doc page 30, decision D6).

Behaviour in cookie mode

  • Login / refresh set Set-Cookie: msm_rt=…; HttpOnly; Secure; SameSite=Strict; Path=/api/v1/auth; Max-Age=REFRESH_TOKEN_TTL_DAYS × 86400, and omit refreshToken from the JSON body. The rotation logic in authService.refresh is unchanged.
  • Refresh / logout read the token from the cookie. refreshSchema body becomes optional in cookie mode. Logout clears the cookie (Max-Age=0).
  • CSRF: when the token comes from a cookie, /auth/refresh and /auth/logout require the header X-Requested-With: metalix and an Origin in CORS_ORIGINS. Otherwise → 403 CSRF_CHECK_FAILED. Cross-site forms cannot set custom headers, and CORS blocks cross-origin fetches.
  • CORS: credentials: true and allowedHeaders include X-Requested-With and Idempotency-Key. Env validation rejects CORS_ORIGINS=* in cookie mode.
  • Cookie parsing: add cookie-parser (one small, widely used dependency), mounted only on the auth router.

Tests: login sets the cookie and omits the body token; refresh via cookie rotates the cookie and the old one fails; missing header → 403; both mode accepts body or cookie; body mode matches today's tests byte for byte.

B17Idempotency keys on create endpointsP2BE
POST/companies · /materials · /purchases · /sales-pos · /sales  +  header Idempotency-Key

Why. On a flaky yard connection the request may succeed while the response is lost. "Try again" then creates a second purchase. With a key, the retry returns the first result instead (UI doc page 30).

Rules

  • The header is optional; without it, behaviour is unchanged. Format: 8–100 chars [A-Za-z0-9_-] (the frontend sends a UUID v4).
  • New model IdempotencyKey: { userId, key, method, path, requestHash, state: IN_PROGRESS|COMPLETED, responseStatus, responseBody, expiresAt }, unique (userId, key), TTL on expiresAt (24 h). Created in migration 002/003.
  • Middleware src/middleware/idempotency.js, placed after authorize and before validate on the five routes:
SituationResult
New keyInsert IN_PROGRESS, run the handler. On 2xx store COMPLETED + response. On any error delete the record, so a corrected retry can run.
Same key, same path + body hash, COMPLETEDReplay the stored status and body with header Idempotent-Replayed: true. Nothing is written.
Same key, still IN_PROGRESS409 IDEMPOTENCY_IN_PROGRESS with Retry-After: 2.
Same key, different body or path422 IDEMPOTENCY_KEY_REUSED.
IN_PROGRESS older than 60 sTreated as abandoned (process crashed) and taken over.

Known limit: if the process dies after the business transaction commits but before the response is stored, a retry more than 60 s later can create a duplicate. Closing that fully means writing the key inside each service transaction, which is a larger change. The middleware already covers the common case: a lost response on a live server.

Tests: two identical POSTs with one key create one purchase and the second has the replay header; a different body → 422; concurrent same key → one 201 and one 409; a failed request (409 stock) can be retried with the same key after stock arrives.

F10 · Query keys and what to refresh after each save

Saves wait for the server on stock and money (UI doc P0-9), then invalidate exactly these keys. Missing one leaves a stale number on screen; invalidating everything makes the app feel slow on weak data.

AfterInvalidate
Purchase create / editpurchases, dashboard, materials (position), source-stock, capacity, company-stats, activity, trend, rates, last-rate
Sale create / editsales, sales-pos, sales-po-summary, sales-po:{id}, dashboard, materials, source-stock, capacity, company-stats, activity, trend, rates
Sales PO create / edit / cancelsales-pos, sales-po-summary, sales-po:{id}, dashboard, materials, capacity, company-stats, activity; plus sales when company or material changed (cascade)
Company create / editcompanies, company:{id}, company-stats; names shown in lists refresh on their next fetch
Material create / editmaterials, material:{id}, dashboard (opening stock changes position)

Stale times: masters 5 min · lists 30 s · dashboard 60 s (the UI doc refetches every 60 s) · capacity 0 (always fresh) · activity 30 s.

F11–F14 · Smaller client items

F11 · URL filters with ids

Filters are stored as ?companyId=66f…&materialId=66f…. The chip shows the name from the cached master list ("Supplier: Shree Ganesh Metals ×"). An unknown id (deleted or deactivated) shows "Unknown supplier" and can still be cleared. No backend slug field.

F12 · Export button

Calls B14 with the current URL query using fetch plus the Bearer header, receives a blob and saves it with the Content-Disposition filename. A plain link cannot carry the token. A spinner shows on the button; 422 EXPORT_TOO_LARGE goes through F9.

F13 · Purchase "last rate" default

When supplier and material are both set and the rate is still empty, the form fills it from B5 and shows the muted line "Last rate from Shree Ganesh: ₹34,500.00 on 27/09/2026". If scope is MATERIAL: "Last rate for HMS 1 (any supplier)". It never overwrites a typed rate.

F14 · Cookie session and idempotency

When the backend runs AUTH_REFRESH_TRANSPORT=cookie: credentials: 'include' on auth calls, the X-Requested-With: metalix header, and the refresh token is never stored. On every create: Idempotency-Key = a UUID made when the form opens. It is reused by "Try again", and a new one is made after success or when the user edits a field.

The one test that matters most

Capacity parity, randomised. Build a random ledger (purchases, POs and deliveries on random past dates across 3 suppliers). Then, for 50 random (PO, supplier, date) picks, call /sales/capacity and assert that a delivery of exactly maxAllowedTons is accepted and maxAllowedTons + 0.001 is rejected. Roll back between picks. If this passes, the panel and the server can never disagree.
