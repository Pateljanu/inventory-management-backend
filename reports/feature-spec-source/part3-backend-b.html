B6Wider searchP1BE

Why. The POC searched purchases by material, supplier, invoice and vehicle, and sales by customer, "stock from" supplier, PO number, material, challan and vehicle. The UI doc's search box says "Supplier, vehicle or invoice no." The backend only searches invoice/challan and vehicle.

ListSearch matches (case-insensitive, contains)
purchasesinvoice no., vehicle no., supplier name, material name
saleschallan no., vehicle no., customer name, stock-from supplier name, material name, PO number
sales-posPO number, customer name, material name
companiesname, GST, contact phone, contact person, contact email, address (city)
materialsname, notes

Implementation

  • New src/utils/search.js: idsMatching(repository, text, field = 'name', cap = 200) returns ObjectIds of masters whose name matches (masters are small; capped). codeRegex(text) = escapeRegex(normalizeCode(text)).
  • Each list service builds $or from these: e.g. purchases [{normalizedInvoiceNumber: codeRegex}, {vehicleNumber: codeRegex}, {companyId: {$in: supplierIds}}, {materialId: {$in: materialIds}}]. Sales add poId: {$in: poIds} from a PO-number lookup.
  • Bug fix included: vehicle and invoice numbers are stored in code form (GJ03AX4521), but search uses normalizeText, so typing "GJ 03 AX" finds nothing today. Code fields must be searched with codeRegex.
  • Search requires at least 2 characters (Zod .min(2)); shorter input is ignored by the frontend.

Scale note: contains-regex scans are fine at yard scale (tens of thousands of rows). If lists grow past ~200k rows, add a MongoDB text index; the API contract does not change. Tests: one per new field; "GJ 03 AX" matches GJ03AX4521; regex characters in input are escaped; search combines with the other filters (AND).

B10Activity feedP1BE
GET/api/v1/reports/activity?limit=20&cursor&types=PURCHASE,SALE,SALES_PO

Why. Both the POC and the UI doc show "Recent activity" (purchases, deliveries and new orders, newest first). Lists are ordered by business date, so a backdated entry would never show as recent; the feed orders by createdAt.

    "company": { "_id": "…", "name": "Rajkot Alloys" }, "material": { "_id": "…", "name": "MS turnings" },

B11Bought vs delivered trendP1BE
GET/api/v1/reports/trend?from&to&bucket=week&materialId&companyId

Why. The UI dashboard chart "Bought vs delivered per week (t)" answers "are we buying faster than we deliver?".

{ "bucket": "week", "from": "2026-09-01", "to": "2026-09-27",
  "series": [ { "start": "2026-09-01", "end": "2026-09-06", "purchasedTons": "96.420", "purchaseValue": "…",
                "soldTons": "88.100", "salesValue": "…" },
              { "start": "2026-09-07", "end": "2026-09-13", … }, … ] }
  • bucket: day | week (Monday start, as in the mockup: 07–13 Sep) | month. Defaults when from is absent: last 8 weeks, last 30 days or last 12 months, ending at to or business today.
  • Two aggregations using $dateTrunc: { date, unit, startOfWeek: 'monday', timezone: 'UTC' }. UTC is correct because business dates are stored at UTC midnight. Missing buckets are zero-filled in code; the first and last buckets are clipped to from/to. Requires MongoDB ≥ 5.0 (Atlas and the test replica set both qualify).
  • Maximum 400 buckets, otherwise 422 VALIDATION_ERROR ("choose a larger bucket").

GET/api/v1/reports/rates?from&to&materialId&bucket

Why. The POC "Rate Analysis" page (overall and material-wise weighted average buying and selling price, difference in ₹ and %, a "check one material" view), plus the UI doc's rate trend chart (page 30, "Medium").

  "overall": { "purchasedTons": "…", "purchaseValue": "…", "averageBuyingRate": "36120.40",
              "soldTons": "…", "salesValue": "…", "averageSellingRate": "41210.75",

  "series": [ { "start": "…", "end": "…", "averageBuyingRate": "…", "averageSellingRate": "…" }, … ] }  // only with bucket + materialId
  • All averages are weighted (value ÷ tons) with avgRate(). difference and differencePct are null unless both bought and sold tons are > 0 in the period (POC hasBoth). differencePct = difference ÷ averageBuyingRate × 100, 2 dp.
  • Selling value uses the stored totalAmount, which is the rate actually billed (poRateAtSale), not the live PO rate. This follows decision D1 and differs from the POC.
  • overall.blended: true tells the UI to label the overall difference "Blended (mixed materials)" (decision D3).
  • series reuses B11's bucketing; it requires materialId, because a series across materials would be the blended number again.

Tests: weighted average vs simple average differ and the weighted one is returned; one-sided material gives null difference; rounding at 2 dp; the series bucket average equals the period average when there is one bucket.

B13Migration 002P1BE

New file src/db/migrations/002-activity-and-idempotency.js, appended to the list in migrations/index.js (never edit 001).

export const id = '002-activity-and-idempotency';
export const description = 'createdAt indexes for the activity feed; idempotency key collection';
export async function up() {
  for (const model of [Purchase, SalesPO, Sale, IdempotencyKey]) {
    await model.createCollection();
    await model.syncIndexes();
  }
}

Declare every index in the schema, not only in the migration

Migration 001 uses syncIndexes(), which drops any index not declared in the Mongoose schema. So schema.index({ createdAt: -1, _id: -1 }) is added to Purchase, SalesPO and Sale, and 002 syncs them. An index created only inside the migration would be silently removed by the next sync.

The IdempotencyKey model belongs to B17. If B17 is postponed, ship 002 without it and add 003 later. Tests: database.test.js asserts the new indexes exist and that running the migrator twice is a no-op.
